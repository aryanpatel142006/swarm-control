swarm-control
the plan, for one last look

A small harness that lets two teammates run several AI coding agents in parallel across two laptops, with Notion as the shared board and GitHub as the truth, to build the selective-hearing project without one giant model session eating the token budget.

Agents execute autonomously in fresh, bounded contexts.
Humans own intent through Notion.
Merged, verified code is the only proof of progress.

What you get

One command on each laptop. Tasks flow from a plan to Notion to the best agent to a reviewed PR to main, with questions surfacing in Notion when a human is needed.

Why it saves tokens

Every task is a fresh, size-capped session. Cheap work goes to cheap models and other providers. Fable and GPT-6 Astra are reserved for critical tasks.

What it is not

Not a framework, not a self-replanning AI company, not the hackathon project. About 3,000 lines of Python plus tests, built and rehearsed before Oct 10.

How to read this

Each section is one idea with one diagram. The diagrams show the real mechanism, not decoration. If a section looks wrong, say the number and what to change. Everything here is also in the written spec, which is what the build plan will be generated from.

What I need you to decide after reading: (1) green light on the design as a whole; (2) whether the default agent roster and strength scores in section 05 look right for the two of you; (3) whether laptop A (yours) is the one that runs the control loop and the orchestrator session.
01

The problem this solves

One long Fable session accumulates context, gets slower and more expensive every turn, and hits the 5-hour limit before the product is done. The swarm replaces one long session with many short, bounded ones, spread across providers.

What you asked for

One orchestrator that splits a plan into tasks in Notion. Each AI takes tasks from its column, works on a branch, reports back, and the orchestrator merges. A reviewer watching everything. A Notion view where agents ask you questions. Shared docs so every agent knows the whole app. The best AI and model for each kind of task.

What I changed and why

Columns are the output of routing, not fixed lanes, so the best agent gets each task. A small Python tool drives the loop deterministically instead of trusting a model to remember to loop. Merges are automatic when checks pass, manual in the last hours. Your friend's plan supplied worktrees, typed reports, debt tracking, and evidence over claims; I dropped the parts two people can't run in a day.

02

The system at a glance

Three processes, two shared services. Notion is where humans look and steer. GitHub is where code lives. Each laptop runs one worker process for all its agents; one laptop also runs the control loop and the orchestrator session.

ProcessWhereJob
swarm runone per laptopPolls the board once per cycle for all agents on this host. Each agent thread: claim a task, make a worktree, build a prompt, run the CLI headless, verify, push, open a PR, report.
swarm servelaptop A onlyRecovers dead tasks, relays your answers to blocked tasks, promotes tasks whose dependencies merged, runs the reviewer, merges, reroutes around rate limits, rewrites the status page every 15 minutes.
orchestrator sessionlaptop AInteractive Claude Code in the project repo. Turns PLAN.md into tasks a milestone at a time, reads the status page, re-plans, answers questions. Never reads code.
03

What lives in Notion

Three databases and one page, created by swarm init with board views already configured. Humans only ever type in two fields: a question's Answer, and its Needs Follow-up checkbox. Everything else is written by the tool, and dragging a card between agent columns is respected.

Tasks

ID, title, description, acceptance criteria, type, importance, size, milestone, priority, agent, model, effort, status, depends-on, scope (globs the worker may edit), feedback, branch, PR, attempts, timestamps. Reports append to the page body per attempt.

Questions

Question, kind (blocking or fyi), context, options, "proceeding with", impact, linked task, asked by, status, Answer, Needs Follow-up. The Open column is your inbox.

Agents

Name, provider, laptop, status (idle, running, cooldown, offline), current task, last heartbeat, cooldown-until, runs, tokens in and out, cost. Both laptops see each other's health here.

Notion has no atomic "claim". Contention is avoided by design because each worker only claims cards in its own agent column, and guarded by writing a random nonce, waiting 1.5 s, and re-reading. All writes retry on rate limits honoring Retry-After.

04

Life of a task

A task moves through a fixed set of states. Every transition is made by the tool, from evidence, never from an agent's claim that it is done.

What "done" means

The branch was rebased on the latest main, the fast verify script passed on the rebased tree, the PR was squash-merged, and the task's decisions and temporary hacks were appended to the repo's decision and debt logs. Not "the agent said it finished."

When review is skipped

Default policy reviews critical and high tasks, anything that touched the contracts or design docs, anything with a missing report, and anything that edited files outside its scope. Normal and low tasks that pass verify merge directly. In the last four hours you flip the policy to review everything and merge by hand.

06

The worker loop

One swarm run per laptop. It polls once for all its agents, hands each task to a free slot, and runs the eight steps below in an isolated git worktree. The model only edits and commits; the tool pushes, opens the PR, and reports.

Why a tool drives the loop

A model asked to "keep looping" forgets, drifts, or stops. A 300-line Python loop does not. It also gives you restarts: kill it, start it again, and it resumes from the board.

Why the model never pushes

Codex stays in its write-only sandbox, Claude needs no network permission, and nothing an agent does can reach GitHub except through the tool with your own gh login.

07

The control loop: review, merge, recover

swarm serve runs on laptop A every 30 seconds and does the seven things below, in order. It is the "agent that constantly reviews all the work" you asked for, split into a deterministic part (verify, rebase, merge, recover) and a model part (the reviewer).

Merge, exactly

Fresh worktree of the branch, rebase onto main, run fast verify on the rebased tree, force-push with lease, squash-merge via gh, mark Done, append the task's decisions and debts to docs/DECISIONS.md and docs/DEBT.md, then promote dependents. Conflicts go back to the same worker with the file list.

Two modes

Automatic merging is the default because a broken main is caught by the verify script before it lands. At T-4h you switch to --manual: serve lists Merge Ready PRs and you pick which land. Only one serve can run; a lock row in the Agents DB stops a second one.

08

The human channel

Agents never stop for reversible decisions. They ask in Notion in two ways, and you answer in Notion or in the orchestrator session. Both write the same field, and the control loop carries the answer to the right task within 30 seconds.

Who asks

Workers (stuck, or a high-impact call), the reviewer (escalate after two rounds), and the planner (ambiguity in PLAN.md).

Where it shows

Questions board, Open column, sorted by impact. Also the "Needs you" line on the status page and in swarm status.

Paper trail

Every decision agents report is appended to docs/DECISIONS.md on merge, so the pitch and judge Q&A have receipts.

Rules, security, and disclosure

HackRU and MLH rules (verified)

  • Oct 10–11, 2026, Busch Student Center, 24 hours, hacking 12:00 PM Saturday to 12:00 PM Sunday, teams of up to 4.
  • Fall 2025 rules (2026 not yet posted): "You are not allowed to submit a project that has been built before the start of hacking." MLH standard rules add that teams may use libraries, frameworks, and open-source code, and must allow generative AI tools.
  • MLH asks teams to be transparent about AI tools used, listing them in the submission.
  • Judging: functionality and execution, creativity and innovation, technical difficulty. In-person table judging, no demo video required, one track only.
How we stay clean: swarm-control is a dev tool in its own public repo, dated before Oct 10, never submitted as the project. The project template contains only structure, empty docs, and verify scripts, no product code. The Devpost writeup lists the harness and every model used. I'd still email the organizers a one-liner to confirm; it costs nothing.

Security and blast radius

  • Worker CLIs run with full tool permission, but only inside a worktree of the project repo. Never run swarm run from a home directory.
  • Secrets are environment variables. .env is gitignored. Prompts never include them.
  • Codex keeps its workspace-write sandbox. Claude's bypass mode is accepted for a hackathon.
  • Only the tool pushes and merges, using your own gh login. Models never touch the network.
  • Nothing deletes branches except the squash-merge cleanup after success.
  • Notion: one internal connection token shared by both laptops, scoped to one parent page. Teammate joins as a page guest so a free workspace's 1,000-block cap for multi-member workspaces doesn't apply.

Testing and rehearsal

Four layers, from no-network unit tests to a real two-laptop rehearsal. The harness is "ready" only when the last layer has been run once, end to end, in under 90 minutes from kickoff to first merged PR.

What rehearsal tunes

Turn and minute caps per task size, the Claude concurrency ceiling on your plan, soft caps, and whether the Antigravity adapter works headless. These are the numbers I can't know without running it.

What I'll report after it

A short table: tasks run, tokens per size, time per size, failures and how they recovered, and the config I changed. If something doesn't hold up, you'll hear it before Oct 10, not during.

18

Research this is based on

Four research passes on Sep 26, 2026, against official docs, leaderboards, and primary sources. Nothing in the design rests on memory alone.

Patterns that every working system converged on

  • Worktree per task, branch named after the task, cleanup on done. ApiariTools/swarm, claude-squad, vibe-kanban, Conductor, Codex app.
  • Leased claims with bounded retries; a reaper requeues stale work. desplega-ai/agent-swarm, the only open-source project found with real multi-machine workers.
  • Durable progress files that every session reads first. Anthropic's long-running-agent harness (Nov 2025) and its quickstart.
  • One task per fresh context, capped iterations, tests as backpressure. The "Ralph" loop and Anthropic's plugin.
  • Separate the agent doing the work from the agent judging it. Anthropic, Mar 2026: "a strong lever," and evaluators only pay off near the capability boundary.
  • Keep a blocked / needs-human status. The one published Notion-to-Claude-Code pipeline was abandoned for lack of it.

Facts verified against primary sources

  • Notion API version 2026-03-11: data sources, database and view creation, markdown page endpoints, 180 req/min, no compare-and-set, webhooks need a public URL.
  • Claude Code 2.1.283 headless flags, structured output, effort levels, session resume, and the reported 429 behavior around six concurrent sessions.
  • Codex 0.157.1 exec flags, JSONL output, sandbox modes, reasoning effort, per-5-hour message estimates by plan.
  • Gemini CLI personal-account shutdown (Jun 18, 2026) and the move to Antigravity; Grok Build headless mode.
  • WebDev Arena (Sep 25, 2026), Terminal-Bench 2.1, MLE-bench, and 2026 practitioner comparisons behind the routing defaults, with the caveat that benchmark boards disagree and the newest models are days old.
  • HackRU Fall 2026 dates and format; Fall 2025 rules; MLH member-event rules on prior work and AI tools.
Your teammate's PLAN.md supplied the invariants this borrows: worktrees, typed reports, debt records for every shortcut, decision receipts, evidence over claims, and a planner that stays high-level. What it left out on purpose: leases as a service, a capacity controller, a steering compiler, a chronicler agent, and an event bus. Two people in 24 hours need a tool, not a company.
