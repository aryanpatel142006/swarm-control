- Q-523 (stale slot entries): swarm-lock listed `harness T-179 verify_fast (pid 14691)` and `T-208 (pid 1363)`, the pids of `swarm serve` and `swarm run`. Two things were mixed up: serve and the runners run their own verifies in-process, so their pid is a real holder while that verify runs; but a waiter killed with SIGKILL/SIGTERM left its `exclusive-pending-<pid>` file behind, and once that pid was reused the file blocked every normal verify. Fix: entries record the process start time (`pstart`, from `ps -o lstart`); an entry is stale when the pid is dead or its start time no longer matches, and stale pending files are deleted on sight. Cleared by hand at 01:50 UTC: four dead `exclusive-pending-*` files (T-110 from Oct 6, T-129, T-151, T-206). The two `verify-*.holder` entries were live (serve running verify_full for T-199 and `_main-verify-T-180`; lsof showed serve holding both flocks) and were left alone.
- Q-523 (orphaned batch): killing a queued swarm-lock let the batch it wrapped start anyway, in parallel with the restarted one. Fix: SIGTERM/SIGINT/SIGHUP while queued exits 128+sig without running the command; while the command runs, the signal stops its whole process tree (descendants listed before the root goes). SIGHUP stays ignored under nohup.

A retry on another laptop only sees the SHA in the error.
